# Morph Protocol v0.1 — Состояние соединения

> Этот документ является частью канонической русскоязычной спецификации Morph Protocol. При расхождениях с переводами приоритет имеет версия из `spec/ru/`.

Соединение Morph Protocol управляется явной state machine.

## Состояния

```text
CONNECTED
   |
   | HELLO
   v
NEGOTIATED
   |
   | AUTH
   v
AUTHENTICATED
   |
   | READY received
   v
READY
```

Повторно подключающийся аутентифицированный клиент может перейти к синхронизации с помощью `RESUME` до продолжения обычной обработки событий.

## 1. Транспорт подключён

После установления WebSocket-транспорта сервер ожидает `HELLO`.

До принятия корректного `HELLO` клиент MUST NOT отправлять прикладные команды.

## 2. HELLO

Клиент отправляет:

```json
{
  "op": "HELLO",
  "protocol": "0.1",
  "client": {
    "name": "Morph Desktop",
    "version": "0.1.0"
  },
  "capabilities": []
}
```

Сервер проверяет совместимость протокола и отвечает `HELLO_ACK`.

Пример:

```json
{
  "op": "HELLO_ACK",
  "protocol": "0.1",
  "session_id": "01K00000000000000000000000",
  "heartbeat_interval_ms": 30000,
  "capabilities": []
}
```

Если совместимой версии протокола нет, сервер возвращает `ERROR` с кодом `UNSUPPORTED_PROTOCOL` и SHOULD закрыть соединение.

## 3. AUTH

После `HELLO_ACK` клиент проходит аутентификацию.

В v0.1 формат аутентификационных данных намеренно оставлен абстрактным. Реализация может использовать существующую систему аутентификации аккаунтов Morph.

Пример:

```json
{
  "op": "AUTH",
  "token": "opaque-authentication-token"
}
```

Клиенты, серверы, шлюзы и отладочное middleware MUST NOT записывать аутентификационные данные в логи в открытом виде.

## 4. READY

После успешной аутентификации сервер отправляет `READY`.

```json
{
  "op": "READY",
  "session_id": "01K00000000000000000000000",
  "user_id": "01J00000000000000000000000"
}
```

Получение `READY` означает, что клиент может отправлять прикладные команды.

## Некорректный порядок

Сервер MUST отклонять пакеты, недопустимые в текущем состоянии соединения.

Примеры:

- `COMMAND` до `READY`;
- `AUTH` до `HELLO_ACK`;
- повторный `HELLO` после согласования;
- прикладные пакеты после отзыва аутентификации.

Сервер SHOULD вернуть:

```json
{
  "op": "ERROR",
  "code": "INVALID_STATE",
  "message": "Packet is not valid in the current connection state."
}
```

Повторные или явно злонамеренные нарушения состояния MAY привести к немедленному закрытию соединения.

## Heartbeat

После `HELLO_ACK` сервер сообщает ожидаемый heartbeat interval.

Точная форма heartbeat-запроса и ответа определяется спецификацией пакетов. Сторона, не выполняющая требования проверки активности в пределах допуска реализации, может быть отключена.

## Resume

После аутентификации клиент, сохранивший состояние синхронизации, может отправить `RESUME` с последней успешно применённой последовательностью событий.

Пример:

```json
{
  "op": "RESUME",
  "after": 1582
}
```

После этого сервер может повторно передать пропущенные события. Если безопасно восстановиться с запрошенной последовательности уже невозможно, сервер MUST указать на необходимость полной синхронизации вместо молчаливого пропуска состояния.
